# Improvement plans: AWS Operational Readiness Review 2.0.3

Generated by `python3 -m tools.orrlens docs` from `lens-src/`, the source of the release file `orr-core.json`. Do not edit by hand.

What to do when a statement is not in place, for the findings report. The questions and risk rules are in `lens-core.md`.

## `well_architected`

- `wa_current`: Run or refresh the Framework review in the AWS Well-Architected Tool with the people who own the design, answer every question against the architecture as it is today, save a milestone, and schedule the next review for 12 months later or the next major architecture change, whichever comes first. Attach the review date and milestone name to the ORR evidence.
- `wa_hri_dispositioned`: Export the open high-risk issues from the improvement plan, give each one an owner role and a target date in your backlog, fix those that are launch-blocking for this workload, and take any you will not fix to the accountable owner for written acceptance with an expiry date. Review the list again at each milestone and before the launch decision.
- `wa_lenses_applied`: Compare the Lens Catalog, and the AWS lenses distributed as custom lens files, with the workload's technology and industry. Add the relevant lenses to the workload, answer them before the launch decision, and disposition their high-risk issues.

## `architecture_failure_models`

- `sm_diagrams_journeys`: Draw the current architecture and data flows from your infrastructure as code and from observed traffic, list the critical journeys and APIs with the dependencies each one uses, store both with the code, and update them in the same change that alters the architecture.
- `sm_fma_documented`: Run a structured analysis, for example with the resilience analysis framework or Failure Mode and Effects Analysis (FMEA): walk each component and dependency through each failure category, record the impact and the protections that already exist, rank the gaps, and schedule a review every 12 months and after major changes.
- `sm_fma_detection`: Add a detection column to the failure mode analysis, map each failure mode to an existing alarm or canary, create alarms for the gaps, and confirm each mapping by injecting the failure in a test environment or by replaying a past incident.
- `sm_fma_mitigation`: Add a mitigation column, link each failure mode to the control, automation or runbook that handles it, write runbooks for the gaps, and put design changes for failure modes with high customer impact and no mitigation on the backlog with an owner and a date.

## `architecture_recovery_dependencies`

- `rp_dataplane_recovery`: List every action in the failover and recovery runbooks and classify each API call as control plane or data plane. Replace control-plane steps with pre-provisioned resources and data-plane mechanisms such as Route 53 health checks or ARC zonal shift, pre-scale or reserve the capacity the remaining locations need, and prove the plan in a failover test that does not use the replaced control-plane actions.
- `rp_no_cross_region_cp`: Trace each critical call and each recovery step to the Region and the plane it uses. Switch clients to Regional AWS STS endpoints, replicate or cache configuration and secrets in each Region, remove calls to global-service control planes from the request path and the runbooks, and create ahead of time anything those steps used to create.
- `rp_no_shared_fate`: List what more than one Availability Zone, cell or Region uses (for example a shared database, a global configuration file, one certificate, or one deployment that targets everything). Split those items per fault boundary where it matters, or stage their changes one boundary at a time with automatic rollback, and keep a last known good copy in each location.
- `rp_prod_isolated`: Move production resources into dedicated accounts under a production organizational unit, attach service control policies that deny disabling logging and deny unapproved Regions, and remove access paths that let non-production identities or pipelines change production.

## `architecture_retry_timeouts`

- `rt_timeouts`: Inventory every client and driver and record its current timeouts. Measure latency per dependency, set connect and request timeouts from those measurements instead of relying on defaults, emit a timeout metric per dependency, and add a test or code review check that fails when a client is created without explicit timeouts.
- `rt_bounded_backoff`: Find every retry mechanism in code, SDK configuration, queues, functions and workflows. Cap the attempts, add exponential backoff with jitter, send exhausted asynchronous work to a dead-letter queue with an alarm, and run a test with a dependency failing to confirm that retries do not multiply traffic.
- `rt_retry_budget`: Map the call chain and remove retries from all but one layer. Enable a retry quota or budget in that layer. Add a circuit breaker only where a dependency can stay unhealthy for long periods, and test it, because circuit breakers add modal behavior. Alarm on the retry rate per dependency, and use client-side rate limiting to stay within third-party limits.
- `rt_idempotent`: List the mutating APIs and message handlers. Add an idempotency key that the server stores with the result for a retention window, return the original result for duplicates, pass client tokens on AWS API calls that accept them, and switch batch handlers to report partial failures.

## `architecture_dependency_failure_handling`

- `df_soft_deps_nonblocking`: List every non-critical call on the request path. Move each one off the path (asynchronous, buffered or cached with a bounded size), give it a short timeout and a defined behavior on failure, and verify by blocking each dependency in a test environment. For Amazon ECS, choose blocking or non-blocking log delivery deliberately for each container.
- `df_degrade_static`: For each soft dependency, agree the degraded behavior with the product owner. Implement it so the normal path already tolerates the dependency being absent, for example by using pushed or cached data on every request, remove rarely exercised fallback code where you can, and test each degraded mode.
- `df_backlog_recovery`: Estimate the backlog that your longest expected dependency outage creates. Set consumer rate limits and maximum message ages, decide which work to drop, prioritize or dead-letter, and rehearse recovery by pausing a consumer or dependency under load and watching the drain.
- `df_faults_injected`: Write a hypothesis for each dependency failure mode, run experiments with stop conditions tied to alarms, start in a test environment, fix what breaks, and add the experiments to a regular schedule or a pipeline stage.

## `architecture_hybrid_connectivity`

- `hy_none`: If any critical-path dependency is reached over a private link, clear this statement and answer the other statements. Recheck at every architecture change, because new integrations often add a private link.
- `hy_redundant_paths`: Map every private link and the devices, locations and providers behind it. Add a second path with no shared component: a second Direct Connect location (the AWS Direct Connect Resiliency Toolkit guides this) and, for the most critical paths, a Site-to-Site VPN backup over the internet sized for critical traffic, because two Direct Connect locations still share the Direct Connect path into the Region. Run BGP on both paths, and alarm on connection and tunnel state (for example the Direct Connect ConnectionState and VPN TunnelState metrics).
- `hy_failover_tested`: Schedule a failover test at least yearly and after network changes: announce it, take down the primary BGP session or connection in a low-risk window, measure time to converge and critical-path latency and errors over the backup path, restore the primary, and track fixes to closure. Add the scenario to your game day plan.
- `hy_onprem_deps`: List every on-premises and partner dependency on the critical path, agree recovery objectives with each owner, and get evidence of a recent recovery test. Where an owner cannot meet the workload's objectives, remove the hard dependency or add a degraded mode, and record the residual risk.

## `architecture_defensive_throttling`

- `tp_per_source_limits`: Inventory every entry point and caller type. Set per-caller quotas and rate limits from load test results, enforce them as close to the edge as possible, return a retryable throttling error, and alarm when a caller is throttled persistently. Document how a caller requests a higher limit.
- `tp_shed_early`: Measure the concurrency at which latency degrades and set admission limits below it. Prioritize health checks and critical calls, return fast errors for rejected work, bound every queue by size or age with a dead-letter destination, and confirm the behavior with a load test that exceeds capacity.
- `tp_dynamic_limits`: Move limits into dynamic configuration with validation and a safe deployment strategy that rolls back on alarms, add runbook steps to change a limit and to block a caller, rehearse both in a game day, and record how long they take.
- `tp_surge_tested`: Add a single-tenant surge scenario to the load test plan: ramp one caller to several times its limit, record per-caller latency and errors, verify throttling metrics and alarms, and fix any shared bottleneck the test exposes, such as connection pools, databases or downstream quotas. Run high-volume tests within the Amazon EC2 Testing Policy.

## `architecture_edge_protection`

- `ep_not_internet_facing`: If any endpoint is reachable from the internet, including through a third-party CDN or front door, clear this statement and answer the other statements. Recheck when new entry points are added.
- `ep_waf_rate_rules`: List every internet-facing endpoint and associate a web ACL with each HTTP endpoint. Add AWS managed rule groups and a rate-based rule per entry point, aggregating by IP, forwarded IP or a custom key such as an API key header. Run new rules in Count mode against real traffic, then switch them to Block, and keep web ACLs in infrastructure as code. For non-HTTP endpoints, restrict sources with security groups and network ACLs, and consider AWS Network Firewall.
- `ep_l7_detection_pages`: For each web ACL, alarm on rate-based and managed rule metrics against a baseline, and on DDoSAttackRequests where the Anti-DDoS managed rule group runs. Route the alarms to your paging system and link each one to the DDoS runbook. If you subscribe to Shield Advanced, the subscription includes access to the Anti-DDoS rule group (as of 2026-10-14; check AWS Shield Advanced and AWS WAF pricing for the fees that apply when you add it); keep these AWS WAF alarms too: rate-based rule metrics on every web ACL, and DDoSAttackRequests wherever the Anti-DDoS rule group runs.
- `ep_ddos_runbook`: Write the runbook from the AWS DDoS response guidance: detection signals, decision points, the rule changes to make and who approves them, support case severity and contacts, and communications. Rehearse it as a tabletop at least yearly and after major edge changes, and track gaps. If you subscribe to Shield Advanced, keep SRT access and proactive engagement contacts current.

## `architecture_health_lifecycle`

- `hc_platform_managed`: If any instance, task or pod is on the critical path, clear this statement and answer the other statements. Platform-managed compute still needs alarms and safe deployments, which other questions score.
- `hc_check_and_replace`: For each tier, define a health check that covers the ability to serve, connect it to automatic removal and replacement (Auto Scaling group ELB health checks, an ECS service or a Kubernetes controller), tune intervals and thresholds from observed behavior, and alarm on unhealthy host counts and replacement rate. Test it by failing one unit and confirming it is replaced without customer impact.
- `hc_dependency_safe`: Review each health check: remove calls to shared dependencies from checks that trigger replacement or removal, report dependency health as separate metrics and alarms, confirm fail-open behavior in each load balancer and service mesh, and verify in a test environment that blocking a shared dependency leaves capacity in service.
- `hc_enter_leave_safely`: Add a readiness or validation step to every deployment and launch path, use warm-up or slow start where cold units are slow, make processes stop intake and finish in-flight work on a termination signal, set draining and stop timeouts longer than your longest normal request, and confirm with a deployment under load that no requests fail.

## `architecture_demand_estimates`

- `dem_forecast`: Build the forecast from historical metrics and business plans: choose the scaling unit for each component, record peaks and their timing, add known event dates and growth, and calculate each component's load when one Availability Zone or the primary Region fails. Get the business owner's sign-off, review it quarterly, and use it as the input for quotas, capacity and the load test.
- `dem_quota_headroom`: Inventory the quotas and limits each component can reach, compare them with forecast peak plus failover in every production and recovery account and Region, request increases with enough lead time, alarm on usage at a threshold you choose (for example 80 percent), and recheck after each forecast update. Where supported, use quota request templates so new accounts start with the quotas you need.
- `dem_capacity_ready`: Measure the time to add capacity for each component and compare it with how fast demand ramps. Then pre-provision, schedule scaling ahead of known peaks, or reserve capacity for critical instance types, requesting future-dated Capacity Reservations at least 8 weeks before known peaks. Set Auto Scaling minimums so scale-in cannot remove required headroom, and alarm when running capacity falls below target.

## `architecture_load_testing`

- `lt_tested_at_peak`: Write down forecast peak and the margin you need (for example twice peak, or peak with one Availability Zone lost). Build a traffic model from production logs or business forecasts, generate load from enough distributed sources (for example the Distributed Load Testing on AWS solution or an open-source tool), stub or coordinate third-party calls, and test in a production-like environment. Compare results with latency and error goals, fix what fails, and repeat after every major change. Follow the Amazon EC2 Testing Policy for high-volume tests.
- `lt_breaking_point`: Extend the load test with a stepped ramp beyond your margin until goals are breached, and capture saturation per component (CPU, memory, connections, queue depth, throttles and quota usage). Record the breaking load and the first bottleneck, alarm on or raise the limiting quotas, fix or accept each bottleneck with an owner, and rerun. Confirm that the workload degrades by shedding load rather than collapsing, and that it recovers when load drops.
- `lt_alarms_verified`: Make alarm, scaling and runbook checks exit criteria of every load test: list the alarms and scaling actions expected at each load step, have the on-call engineer observe them live, record which fired, when, and how long scaling took, and fix thresholds, scaling policies or runbooks that did not behave as expected before the next test.

## `architecture_rpo_rto`

- `rec_objectives`: Run a business impact analysis with the business owner: for each critical journey, estimate the cost of downtime and of data loss over time, set RTO and RPO per component, check that dependencies (including third parties and shared platforms) can meet them, and record the approved values. Revisit them at each major change and at least yearly.
- `rec_restore_tested`: Schedule a restore test at least yearly and after major changes: take the latest recovery point of every critical data store, restore it into an isolated account or environment, start the application against it, run data validation and a critical-journey test, and record the elapsed time and the age of the restored data against RTO and RPO. Automate the test where possible and track every gap to closure.
- `rec_strategy`: For each component, compare the DR strategies with its RTO, RPO and budget, choose one, and document the Region decision, the scenarios covered and excluded, residency constraints, the recovery runbook and the dependencies the recovery itself needs. Prefer recovery steps that use data-plane operations and pre-provisioned capacity. Review the strategy when objectives or architecture change. For a pilot light or warm standby strategy, consider On-Demand Capacity Reservations in the recovery Region's Availability Zones for the instances recovery must launch. They are billed whether or not instances run.
- `rec_failover_exercised`: Plan a failover exercise at least yearly: set success criteria from RTO and RPO, run the failover with the documented runbook and tools in a scheduled window (or in a production-like copy until production failover is proven safe), measure time to recover and data loss, fail back, and track fixes. Detect configuration drift between the environments continuously so that the recovery environment matches production.

## `architecture_data_corruption`

- `dc_pitr`: Inventory every data store and classify it by criticality. Turn on point-in-time recovery or versioning where supported, add automated backups elsewhere through a central backup plan, set retention from how long corruption could go unnoticed, and alarm on failed backup jobs and on stores that are not covered. Document which data can be rebuilt from source instead.
- `dc_immutable_isolated`: Create a dedicated backup account, copy critical recovery points to a locked vault there (compliance-mode Vault Lock or a logically air-gapped vault), restrict who can change backup and key policies with permission guardrails such as service control policies, keep backup keys out of reach of production administrators, and alarm on attempts to delete recovery points or change vault, lock or key settings. Test that you can restore from the isolated copy into a clean account.
- `dc_detection`: For each critical store, define what abnormal looks like (delete and overwrite rates, record counts, write volume, encryption or permission changes) and alarm on it; add scheduled integrity checks that compare data with its source of record; turn on threat detection for data stores; scan recovery points for malware; and document in the runbook how to identify the last known-good recovery point.
- `dc_point_restore_rehearsed`: Add a corruption drill to the recovery test plan: in a non-production copy, inject a realistic corruption or deletion, practice finding the last known-good point, restore from the isolated backup copy into a clean environment, run validation, and reconcile later changes. Record the timings, fix gaps in tooling and runbooks, and repeat at least yearly.

## `architecture_cold_start`

- `cs_restart_documented`: Draw the start-up dependency graph, break any cycles (for example by caching or bundling bootstrap data), write the runbook with expected timings, and review it after each major architecture change.
- `cs_artifacts_controlled`: List every external artifact source used at start-up and scale-out (check user data, Dockerfiles, bootstrap scripts and agents), mirror each into a repository you control and replicate it to every Region you use, block direct internet fetches at start-up, and alarm on failed pulls.
- `cs_config_resilient`: List every configuration, secret and flag read at start-up, cache last-known-good values with integrity checks, replicate recovery secrets across Regions, give start-up calls timeouts with safe defaults, and test start-up with the configuration store blocked.
- `cs_exercised`: Schedule a cold-start exercise at least yearly: block egress to the internet and to non-critical dependencies in a test environment (for example with AWS FIS network actions or security group changes), restart or scale out, measure time to healthy, and track fixes to closure.

## `releases_manual_changes`

- `cc_pipeline_only`: Inventory every way production changes today (console, CLI, scripts, configuration tools, feature-flag dashboards, database clients). Move each into version control with a pipeline deployment, restrict human write access as event_mutating_access describes, and alarm when a change is made outside the pipeline.
- `cc_review_enforced`: Turn on protection rules for every repository that feeds production (required review by someone other than the author, no direct pushes, no self-approval, required status checks), apply them to bot and AI agent identities too, restrict who can change the rules or the pipeline's checks, and make the pipeline deploy only reviewed commits from protected branches. Audit regularly for bypasses.
- `cc_preview_drift`: Make the pipeline produce and publish an IaC preview for review, fail or require approval when a change replaces or deletes a stateful resource, and schedule drift detection (for example the AWS Config managed rule cloudformation-stack-drift-detection-check) with an alarm to the owner. Fix drift by changing code, not by hand.
- `cc_emergency_path`: Write the emergency change procedure: who can invoke it, which pipeline controls may be shortened and which never are (review, safety tests, rollback), and how break-glass access is granted, alarmed and revoked. Add a pipeline option that skips only time-based gates with a recorded approver, rehearse the path in a game day, and review every use within a few days.

## `releases_staged_deployments`

- `pp_tests_block`: Add a pre-production stage to every pipeline (code, infrastructure and configuration) that deploys the change and then runs automated integration and end-to-end tests for each critical journey. Make any failed test fail the stage so promotion stops, notify the owning team, and treat flaky tests as defects to fix rather than tests to disable. Review the coverage of critical journeys at each ORR.
- `pp_parity`: Template every environment from the same IaC with per-environment parameters, move pre-production into its own accounts, build each artifact once and promote it by digest or version, and add a pipeline check that fails if the artifact about to reach production differs from the one tested in pre-production. Record any intended difference between environments and why it is safe.
- `pp_build_gates`: Add the missing scan types to the build, run them in report-only mode first to baseline existing findings, agree severity thresholds with the security owner, then make findings at or above the threshold fail the build. Route findings to the owning team, record time-bound exceptions, and review the thresholds at each ORR.
- `pp_perf_regression`: Pick the performance-sensitive paths, define a short, representative load profile, record a baseline from the last good release, run the test automatically in a pre-production stage, and fail promotion when p99 latency, error rate or throughput regress beyond the agreed threshold. Run high-volume tests within the Amazon EC2 Testing Policy.

## `releases_phased_rollout`

- `pd_staged_expansion`: For each change type, choose a native phased mechanism and configure a small first slice followed by automated increments, each gated on health checks and alarms. Remove or restrict any path, such as console edits or direct configuration pushes, that can apply a change everywhere at once. All-at-once deployment is a launch-blocking gap unless the accountable owner formally accepts it, for example for commercial software that supports only in-place upgrades.
- `pd_fault_boundary_waves`: Order Regions or cells from lowest to highest risk, start with a single Region or cell, then promote in waves of increasing size with bake time between waves. Encode the order in the pipeline rather than a runbook, and make each wave wait until the previous one has finished baking with clear alarms.
- `pd_bake_time`: For every production stage, list the rollback alarms it watches and their evaluation time, then set a bake time longer than the slowest of them, longest in the first stages. Watch customer-facing alarms and canaries during each bake, and revisit bake times after any incident that a longer bake would have caught.
- `pd_blockers`: Add a check before each production stage that blocks deployments outside the approved window, on blocked dates and while customer-facing alarms are in ALARM, and document how an urgent fix overrides it with an audit record. Give the blocked-date calendar an owner and keep it current.

## `releases_deployment_rollback`

- `rb_auto`: Pick the native rollback mechanism for each deployment path, wire it to the alarms that represent customer impact, and prove that a deliberately bad change rolls back with no human action. Manual-only rollback is a launch-blocking gap unless the accountable owner formally accepts it, for example for commercial software you cannot redeploy.
- `rb_alarms_scoped`: For each pipeline stage, list the rollback alarms and their evaluation windows, add customer-facing and canary alarms where missing, and add a version dimension to key metrics so the new version can be told apart from the old one.
- `rb_backward_compatible`: Adopt a two-phase (prepare, then activate) pattern for format and schema changes, add a pipeline test that deploys version N+1, writes data, rolls back to N and verifies that N can read it, and document the rules for destructive migrations.
- `rb_exercised`: At least once a year, and ideally each quarter and after pipeline changes, run a planned rollback drill: deploy a harmless change, roll it back with the documented single action, time it, and remove any manual step you needed.

## `releases_security_readiness`

- `sec_testing_closed`: Update the threat model for this release, plan security testing for the new or changed attack surface, run it against a production-like environment within the AWS penetration testing policy, and track every finding to closure. Before launch, fix and retest critical and high findings, or record a time-bound acceptance in your risk register.
- `sec_detection_routed`: If detection is already on, start with the routing step below. Otherwise, enable threat detection and posture findings organization-wide through a delegated administrator, in every Region the workload uses, and restrict unused Regions, for example with service control policies. Add rules that send findings at or above an agreed severity to the owning team's on-call queue, with a runbook per finding type, and generate sample findings to prove the route works.
- `sec_ir_exercised`: Write or adapt playbooks for credential compromise, ransomware and data exposure, run a tabletop exercise on one of them each quarter with the on-call, security and business contacts, and track each gap to closure. Rotate scenarios so that every playbook is exercised at least once a year.
- `sec_audit_logs`: Create an organization trail into a log archive account, add the other log sources investigations need, turn on log file integrity validation and write-once protection such as S3 Object Lock, restrict read access to the security team with audited access, and set retention per mandate. Confirm in an exercise that a responder can query recent logs quickly.

## `underlying_dependencies`

- `dep_inventory`: Build the inventory from architecture diagrams, IaC templates, IAM policies, network flow logs and trace maps, then confirm it with the team. Record each dependency's owner, Regions, and whether it is needed at runtime, at deploy time or only during recovery. Review the inventory at each ORR and after major architecture changes.
- `dep_classified`: Walk each critical journey and mark every dependency hard or soft, with the customer impact of its failure and the intended degraded behavior. Confirm the classification with a test or fault injection where you can, and record each hard dependency that should become soft as a tracked backlog item.
- `dep_partition_verified`: List every service and feature from the inventory and check each one against AWS Capabilities by Region and, for AWS GovCloud (US), the service pages of the GovCloud User Guide. Check the compliance programs you need on AWS Services in Scope by Compliance Program. Record the date and result, design an alternative for anything missing, and repeat the check before each launch and at each recurring review.

## `event_alarms`

- `slo_defined`: For each critical journey and API, agree availability, latency-percentile and completion-time targets with the business owner, set them tighter than any SLA, choose the metric that measures each one from the customer's side, and publish them with an owner and an error budget.
- `slo_alarms_before_breach`: Create an alarm for each SLO on error rate and on latency percentile, with thresholds that fire while error budget remains; consider a fast-burn and a slow-burn alarm per SLO. Route them to the paging rotation, test each one by setting it to ALARM, and keep alarm definitions in IaC.
- `slo_alarm_quality`: Review every paging alarm's period, datapoints to alarm and missing-data treatment, record the reason for each choice, fix alarms that page on a single datapoint or stay quiet when data stops, and check these settings in code review of the alarm IaC.
- `slo_reviewed`: Schedule a recurring operations review with a fixed agenda: SLO attainment and error budget, alarms that fired and whether they were actionable, missed detections, and open action items. Give each fix an owner and a due date and track it to closure.

## `event_canary_alarms`

- `can_coverage`: Map each critical API and journey to a canary, start from a canary blueprint (for example API canary or multi checks for APIs, and GUI workflow builder or canary recorder for browser flows), run it in every Region and entry point every 1 to 5 minutes, and make canary updates part of the definition of done for journey changes.
- `can_own_metrics_alarms`: Create alarms on SuccessPercent and Duration for every canary, with missing data treated as breaching, route them to the paging rotation, and test them by breaking a canary in pre-production. Confirm that a canary failure is detected within your target, for example five minutes.
- `can_independent`: Move canaries and their alarms to a separate monitoring account and stack, add a cross-Region canary for each Region's customer endpoints, send critical notifications through a path that does not depend on the workload's Region, and add a heartbeat alarm that pages when canary data stops.

## `event_saturation_alarms`

- `sat_compute`: List the saturation signals for each compute type in the workload, add alarms with headroom thresholds through IaC or automation that runs when resources are created, and check coverage at each ORR by comparing alarmed resources with the resource inventory.
- `sat_datastore_deps`: Instrument each dependency client to emit latency, error, throttle and timeout metrics per dependency and operation (for example with the CloudWatch embedded metric format), add alarms on those metrics and on provider capacity metrics, and add a critical-dependencies view to the operational dashboard.
- `sat_async_age`: For each queue and stream, set an age threshold from its completion SLO, alarm on oldest-item age and on dead-letter arrivals, and alarm on replication lag for replicated data. Document in the runbook how to drain or redrive a backlog safely.
- `sat_usage_cost`: Add alarms on usage-rate metrics for each entry point and consumer, create Cost Anomaly Detection monitors for the workload's accounts or cost allocation tags, subscribe the owning team, and test that alerts reach that team.

## `event_transaction_tracing`

- `tr_correlated_logs`: Adopt one structured log schema with a required request or trace ID, propagate the ID through every call and message, return it in error responses, centralize logs from all accounts and Regions, and save the incident queries responders need. Keep secrets and personal data out of logs, and mask sensitive fields, for example with CloudWatch Logs data protection policies. Test it by tracing one request end to end from a sample error response.
- `tr_open_tracing`: Instrument each service with OpenTelemetry, starting with automatic instrumentation, propagate context through messaging, choose a sampling policy that keeps errors, and send traces to your tracing backend. Move existing instrumentation that does not use an open standard to OpenTelemetry.
- `tr_alarm_diagnostics`: Add links to dashboards, saved queries and the change log to every paging alarm description, then automate the first diagnostic steps of your most frequent runbooks so they run when the alarm fires and post the results to the incident ticket or channel.

## `event_oncall_rotation`

- `oc_paged`: Define the hours the workload must be supported, staff a rotation with enough trained people to cover them sustainably, connect paging alarms to a paging tool (for example through Amazon SNS to a partner paging service), set and track an acknowledgment target, and send a test page whenever the rotation changes.
- `oc_runbook_per_alarm`: Inventory paging alarms, write a short runbook for each one (starting with the most frequent), put the runbook link in the alarm description, and add a check to alarm code review or CI that fails when a paging alarm has no runbook link. Automate stable runbook steps where it is safe.
- `oc_runbooks_exercised`: Add a last-exercised date to each runbook, schedule drills for runbooks older than 12 months or affected by major changes, run them with on-call roles and permissions, and fix what failed. Combine drills with your game days where possible.
- `oc_escalation`: Configure an escalation policy in your paging tool (primary, secondary, manager), test it by leaving a test page unacknowledged, and document escalation paths and contacts for incident command, management, security and internal dependency owners. Review the contacts at each rotation change.

## `event_provider_escalation`

- `pe_escalation_runbook`: For AWS and each critical provider, document how to open and escalate a case, your severity definitions, the details to include, approvers and contacts. Add at least one fallback that works when the AWS Support Center console and API are impaired, store the runbook and contacts where responders can reach them during a Regional or identity outage, link the runbook from your paging runbooks, and verify each fallback path once a year.
- `pe_support_fit`: List every production account and the support arrangement that covers it, record the target initial-response time for production-down cases, compare it with the RTO of the workloads in that account, and close or formally accept each gap. Re-check after account moves, plan or contract changes and RTO changes.
- `pe_events_routed`: Create Amazon EventBridge rules for AWS Health events in every production account and Region you use, or aggregate events with the AWS Health organizational view and a delegated administrator, and route them to your ticketing or paging tool. Subscribe to the status feeds of critical third-party providers, turn planned lifecycle events into owned work items, and test the routing end to end.
- `pe_changes_staged`: Inventory the provider-managed versions you depend on (engines, runtimes, Kubernetes and platform versions, certificate authorities) with their end-of-support dates, link each to the matching AWS Health or provider notice, and schedule every change through pre-production with your normal tests and bake time before production. Pin or control versions where the service allows, and track each deadline as owned work.

## `event_customer_impact`

- `ci_identify`: Add a customer or tenant identifier to structured logs and key metrics, save queries that list affected customers by error type and time window, test them in a game day, and document who may run and share the results.
- `ci_comms_plan`: Write the plan with your communications, legal and customer-support owners, pre-approve templates for common event types, list notice obligations and deadlines, and check each channel and approver at least once a year, for example with a test notice or in your next exercise.
- `ci_status_independent`: Map the dependencies of your status and notification path, move it to infrastructure that does not share accounts, identity or Region with the workload, or to a separate provider, keep a documented manual fallback, and practice publishing through the fallback in a game day.

## `event_resilience_recoveries`

- `az_regional_managed`: Check your component list against the AWS Fault Isolation Boundaries whitepaper. If any customer-managed zonal resource is on the critical path, clear this statement and answer the other statements.
- `az_multi_az`: Inventory the AZ placement of every tier, including data stores and network paths, remove single-AZ and single-instance components or record a formal acceptance, and add a recurring check, for example AWS Config managed rules for Multi-AZ settings, so new single-AZ resources are flagged.
- `az_static_capacity`: Calculate the capacity each AZ must hold to absorb the loss of one AZ at peak, provision it (with Capacity Reservations for critical instance types if needed), set Auto Scaling minimums so scale-in cannot remove it, and alarm when capacity in any AZ falls below the target.
- `az_tested_at_load`: Plan an AZ-loss experiment with stop conditions on customer-facing alarms. Start in pre-production at production-like load, then move to production with a limited blast radius when you are confident. Record time to detect and recover, and fix anything that needed new capacity. For critical workloads, repeat it at least quarterly or run it in the deployment pipeline (a suggestion).

## `event_az_evacuation`

- `ev_regional_managed`: Check your component list against the AWS Fault Isolation Boundaries whitepaper. If any customer-managed zonal resource is on the critical path, clear this statement and answer the other statements.
- `ev_shift_mechanism`: Enable zonal shift for every supported resource on the critical path, and write a runbook or automation that also covers what ARC does not shift, such as queue consumers, east-west traffic and data store primaries. Measure how long a full AZ evacuation takes against your target, and consider zonal autoshift once every AZ is pre-scaled to carry the load without the impaired one.
- `ev_per_az_detection`: Publish error and latency metrics with an AZ dimension for every zonal tier, alarm when one AZ deviates from the others, and link the alarm to the AZ shift runbook. Then run a partial-AZ experiment with stop conditions in pre-production, and later in production, to prove the alarms fire and identify the AZ.
- `ev_shift_practiced`: Set a time-to-mitigate target for an AZ impairment, schedule practice shifts (ARC practice runs, or at least a quarterly drill, as a suggestion), alarm on customer impact during each one, record detection and mitigation times, and fix what slowed you down. You can combine practice with fault injection, for example by testing zonal autoshift with AWS FIS.

## `event_mutating_access`

- `pa_automation_default`: List the roles and permission sets people use in production, replace standing write access with read-only or view-only defaults (the AWS managed job-function policies ReadOnlyAccess, or ViewOnlyAccess where people should not read data, are starting points), move routine changes into pipelines or reviewed automation, and alarm on mutating API calls made by human roles outside the elevation path.
- `pa_jit_elevation`: Choose a temporary elevated access mechanism, for example a validated partner solution that integrates with IAM Identity Center or the open-source TEAM solution, define who may approve elevation and for how long, log every elevated session, and replace IAM users and long-term access keys used by people with federated sign-in and temporary credentials. If IAM Identity Center is not available for AWS account access, for example because another team controls the organization, federate your workforce identity provider to IAM with SAML 2.0 in one account and assume roles from there (role chaining limits those sessions to one hour), keeping IAM users only for the tested emergency path.
- `pa_root_secured`: Enable MFA and delete access keys for every root user, alert on root activity (for example an Amazon EventBridge rule on AWS CloudTrail events for the root user), enable centralized root access for member accounts and remove their root credentials except where a documented emergency path still relies on them, and document who may run privileged root tasks and how each is approved.
- `pa_access_reviewed`: Schedule access reviews with account owners, review every elevated session, use IAM Access Analyzer unused access findings and last-accessed information to remove permissions nobody uses, give each pipeline, automation and AI agent its own scoped role, and keep the review results as evidence.

## `event_emergency_access`

- `ea_per_failure_mode`: List what responders depend on to sign in (identity provider, IAM Identity Center and its Region, SAML configuration, MFA devices, credential vault) and how each can fail. For each failure mode, write a short runbook with pre-conditions, approvers and steps. Pre-create the emergency account, roles and cross-account trust before you need them (for example with CloudFormation StackSets), protect them with service control policies, and alert on any sign-in or API activity by the emergency roles outside a declared incident.
- `ea_tested_independent`: Schedule a test of every emergency path, including the independent one. Run it from a clean workstation with only the credentials and devices the runbook names, and record the time to access and every gap. Give each emergency IAM user a Regional console sign-in URL, use that URL in the test, and confirm that the MFA type the user holds works through it: the IAM resilience page warns that Universal 2nd Factor (U2F) MFA might not complete. Configure your identity provider for multiple Regional SAML sign-in endpoints, consider IAM Identity Center multi-Region replication (organization instances with an external identity provider or the Identity Center directory, not Active Directory, and a multi-Region customer managed KMS key) so that access provisioned before a disruption keeps working when the primary Region is impaired, and switch scripts and tools to Regional AWS STS endpoints. Repeat the test after identity, Region or account changes.
- `ea_out_of_band`: List where each incident tool is hosted and how people sign in to it, and remove shared dependencies on your identity provider and the workload's primary Region. Keep a current read-only copy of runbooks and contacts in a second location, set up a fallback bridge and chat channel with independent sign-in, give responders an offline contact list, and switch to the fallbacks during your next game day.

## `event_operator_tooling_safety`

- `ot_blast_radius_limits`: Inventory the commands operators run in production and wrap the risky ones in automation runbooks with typed, validated parameters (for example allowedValues or allowedPattern in Systems Manager documents), a target preview, concurrency and error-threshold limits, and a minimum-capacity check that aborts the run. Retire direct use of the underlying commands for those tasks, and add the safety checks to every similar tool.
- `ot_resource_protections`: List the resources whose deletion or replacement would cause an outage or data loss. Turn on deletion or termination protection for each, set retain or snapshot policies on stateful resources in your templates, add stack policies for critical resources, and add a service control policy that denies deletes on resources tagged as protected except through a break-glass or pipeline role. Alarm when a protection setting is turned off.
- `ot_dry_run_two_person`: Classify operator commands by impact. For the high-impact ones, add a preview step that prints the intended actions and targets, and an approval step by someone other than the operator, for example the aws:approve action in a Systems Manager Automation runbook or a manual approval action in AWS CodePipeline. Review approval records and emergency bypasses in your operations review.

## `event_expiring_materials`

- `exp_inventory`: Build the inventory from the sources you can query (ACM and AWS Private CA certificates, Secrets Manager secrets, IAM access keys from the credential report, identity provider metadata, registrar and license records) and add the materials you can only find by asking, such as partner-issued tokens and certificates on devices. Assign an owner and a renewal method to each entry, list every consumer, and reconcile the inventory on a schedule and in your deployment pipeline.
- `exp_alarms`: For each kind of material, pick the signal (ACM metric or event, AWS Config rule, or a scheduled check that reads the expiry date from the served certificate, the secret or the registrar), set the lead time longer than your manual renewal and distribution time, and route it to the owning team's paging or ticket queue. Add alarms on renewal failure, test that each alarm fires, and review open expiry alarms in your operations review.
- `exp_no_leaf_pinning`: Search client code, mobile and device builds, SDK configurations and partner integration documents for pinned certificates or public-key hashes. Replace leaf pins with CA or root pins, or remove pinning, ship the change before the next renewal, and add a check to code review and the pipeline that rejects new leaf pins.
- `exp_auto_renew_deploy`: Move certificates to ACM managed renewal with DNS validation where you can, turn on Secrets Manager rotation for secrets, and automate distribution to every consumer. For materials that cannot renew automatically, write a renewal runbook with owners and lead times. Exercise each rotation in pre-production and then in production on a schedule, and record that clients kept working.

## `event_gameday`

- `gd_fault_injection`: Pick two or three failure modes from your failure model, such as loss of one AZ and loss of a critical dependency, and build each as an experiment with stop conditions on customer-facing alarms, for example from the AWS FIS scenario library. Run it first in pre-production at production-like load, then in production with a limited blast radius, with the on-call engineer responding as if it were real. Record time to detect and to mitigate, and file every gap as a finding. If the platform owner must approve fault injection, request approval early and start with a narrow experiment in a pre-production account.
- `gd_tabletop`: Schedule a tabletop exercise with a facilitator, a written scenario and objectives agreed by leadership. Include the incident lead, on-call engineers, communications and support owners and a business decision maker, and walk through detection, escalation, provider engagement, customer communication and recovery decisions. Capture an after-action report and repeat at least once a year (a suggestion) with a different scenario.
- `gd_people_engaged`: For each exercise, build the participant list from the current on-call schedule and escalation documents rather than from the team that wrote the runbooks, invite the business decision maker and dependency owners, and confirm each person's contact details and access during the exercise. Track who has taken part, and add new on-call engineers to the next exercise.
- `gd_findings_closed`: After each exercise, write the findings as actions with owners and due dates in your work tracker (for example AWS Systems Manager OpsCenter or your ticketing system), review open actions in your operations review, update runbooks, alarms and this lens's answers as actions close, and include a check of past findings in the next exercise.

## `event_post_incident_analysis`

- `pia_process`: Adopt a short template (impact, timeline, contributing factors, detection and mitigation questions, actions), define which events and near-misses require it and the deadline, collect timeline data automatically from alarms, deployments and chat logs, and review each analysis in a recurring meeting with someone outside the owning team. Before launch, run the process on an exercise or on an event from a similar workload. If another team runs the process, take part in the analyses of this workload's events.
- `pia_actions_tracked`: Put every corrective action in the same tracker as other engineering work (for example AWS Systems Manager OpsCenter or your ticketing system) with owner, due date and priority, add an overdue-actions view to your weekly operations review, escalate actions that slip, and require evidence that the fix is in production before closing.
- `pia_orr_feedback`: Add ORR questions to your analysis template. For each gap, draft a question, guidance and links to the analysis, and add it to your own add-on custom lens, starting from the templates/org-addon-lens.json template in this lens's repository rather than editing this lens, so your questions survive lens upgrades. Re-answer the affected questions in this lens.

## `readiness_signoff`

- `rd_highs_dispositioned`: Export the high risks from the review report, give each an owner and a date, fix each one or record a time-bound acceptance in your risk register, and add the EXC tag to the question notes before sign-off.
- `rd_criteria_owner`: Create a one-page launch decision record with criteria, decision owner, abort triggers and rollback steps, and link it from the review notes.
- `rd_scope_complete`: Before sign-off, list the unanswered questions in the lens review, answer each one or mark it not applicable with a reason (console, or UpdateAnswer with IsApplicable, Reason and Notes), and schedule a full-core session if only the core path was covered.
- `rd_next_review`: Compare current answers with the last milestone and update every answer that changes or incidents affect, save the milestone right after answering this question, add a recurring calendar entry for the next review, and set a reminder for each accepted risk's expiry date.
