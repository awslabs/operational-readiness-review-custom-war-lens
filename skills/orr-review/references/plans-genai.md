# Improvement plans: ORR - Generative AI and Agents 1.0.2

Generated by `python3 -m tools.orrlens docs` from `lens-src/`, the source of the release file `orr-genai.json`. Do not edit by hand.

What to do when a statement is not in place, for the findings report. The questions and risk rules are in `lens-genai.md`.

## `gai_inventory_routing`

- `mi_lifecycle_tracked`: List every model call path, read modelLifecycle from GetFoundationModel or ListFoundationModels on a schedule, record end-of-life dates, assign an owner per model, and alarm to that owner when LegacyModelInvocations is above zero. As of 2026-10-07, Amazon Bedrock models launched on or after 2026-09-07 follow the current lifecycle policy (a 6-month or 45-day Legacy period, shown on the model card), and older models follow the Legacy lifecycle page (at least 6 months in Legacy state).
- `mi_successor_ready`: For each Legacy or end-of-life-dated model, pick an Active successor, run the release evaluation on it, recompute token quota needs for it, request the successor's quota increases ahead of cutover (increases are not granted once a model is Legacy), and schedule the cutover with a date before end of life.
- `mi_routing_approved`: Map each call path to in-Region, geographic or global routing, list the destination Regions (for third-party APIs, the provider's processing locations), get written approval from the data owner, and record the inference Region in audit logs (the CloudTrail field additionalEventData.inferenceRegion). This extends the residency constraints in the core disaster recovery strategy statement to where each inference request runs.
- `mi_routing_enforced`: From each production account, with production SCPs attached, send a test request through each routing option the workload uses, add the documented inference-profile exception or the global-routing deny, and keep the test in pre-production so policy changes cannot break routing unnoticed. AgentCore: confirm network configuration and egress rules allow only the approved Gateway and tool targets. Third-party APIs: confirm egress allows the provider endpoints.

## `gai_capacity_quotas`

- `tk_token_sizing`: From load-test and production metrics, compute per-minute quota use as input plus max_tokens at admission and the documented burndown at settlement, add failover load, and compare with granted quotas per model, profile, endpoint and Region. Request increases with lead time (increases are prioritized for accounts already consuming their quota), and add the recomputation to the model-change checklist. On bedrock-mantle, size the separate input and output token quotas. Amazon SageMaker AI and self-hosted: size instances from measured tokens per second. Third-party APIs: use the provider's limits.
- `tk_traffic_isolated`: Inventory every caller of each model in each production account, move bulk jobs to batch inference where the model supports it or to a separate account, and cap the remaining callers below a share that leaves latency-critical traffic its headroom.
- `tk_capacity_option`: Decide the capacity option per journey and record why. If you use the Reserved tier, request it as the service tiers page describes. Test overflow at load, and alarm when requests are served by a tier or capacity option other than the intended one. Amazon SageMaker AI: test what happens when traffic exceeds the instances in service before auto scaling adds more, and alarm on invocation errors and on reaching the maximum instance count. Third-party APIs: check the provider's reserved-capacity overflow behavior.

## `gai_dependency_fallback`

- `fb_stop_reasons`: Add a handler for each stop reason and stream error, unit-test each one with recorded responses, and publish the count of non-normal stop reasons per model and prompt version as a metric that rollouts compare.
- `fb_fallback_parity`: List every fallback, check model access and quota per account and Region, attach an identical guardrail configuration (the same version in the same Region, the same infrastructure as code definition in each fallback Region, or a guardrail cross-Region profile), run the release evaluation and safety tests on each fallback, and record the results with the release. In AWS GovCloud (US), keep export-controlled data out of evaluation job metadata.
- `fb_fallback_warm`: Add a scheduled request for each fallback path with an alarm on failure, or route a small percentage of real traffic to each fallback, and page the model owner when one fails.

## `gai_change_safety`

- `mc_pinned_versions`: Search production configuration and infrastructure as code for DRAFT guardrails, unversioned prompts, floating model aliases, latest image tags and DEFAULT agent endpoints. Replace each with a pinned version, and add a pipeline check that rejects them in production stages. Record the pinned versions with each release so a rollback restores the exact previous set.
- `mc_quality_in_rollout`: Emit quality metrics tagged with the model, prompt and guardrail version that served each request (guardrail interventions, stop reasons, sampled evaluation scores and user feedback). Add them to the stage gates of the rollout next to the error and latency alarms, with a threshold relative to the previous version, so a regression stops promotion and triggers rollback.

## `gai_quality_evaluation`

- `qe_gate_blocks`: List every path that can change a prompt, guardrail, model reference or retrieval index, including console edits, prompt management and scheduled ingestion, and trigger the evaluation from each. For prompt, guardrail and model reference changes, make it a blocking step before promotion. A knowledge base sync writes to the index that production queries, so for retrieval changes either ingest into a staging knowledge base and promote it with a gated change of the knowledge base ID in configuration, or evaluate right after each sync, alarm on a regression and keep a documented way to restore the previous content (for example, re-sync from a versioned copy of the source data). Test each path with a known-bad candidate.
- `qe_retrieval_fresh`: Enable ingestion logging for each knowledge base, create metric filters for failed jobs, failed resources and partly indexed documents, and alarm on them. Publish the time since the last successful sync as a metric and alarm when it exceeds the written freshness target.

## `gai_observability`

- `obs_all_paths`: List every inference endpoint, account and Region the workload uses, including fallback paths. Send a tagged test call through each and find it in the invocation or request logs and in CloudTrail. Turn on what is missing (model invocation logging, CloudTrail data events for bedrock-mantle, request logs in the application or serving layer, which SageMaker AI and self-hosted models need), and alarm on log delivery failures and on a sudden drop in log volume. Logging is configured per Region, so repeat the test call in each Region, and whenever an endpoint, model or Region is added.
- `obs_version_attribution`: Add the served tier or capacity option, the processing Region, the model or inference profile ID, and the prompt and guardrail versions to the structured log schema at the point where the response is received. Check a sample of production logs for the fields, and add them to the incident dashboard so responders can filter by them.

## `gai_safeguards`

- `sg_enforced_outside_code`: Add account or organization guardrail enforcement or an IAM deny, applied to fallback paths too. Do not give a role that carries the IAM condition key extra permissions for APIs such as RetrieveAndGenerate that make model calls on its behalf. Set comprehensive guarding for system prompts and messages, or strip guard-content tags at the entry point. Use synchronous streaming where blocking or masking is needed (asynchronous streaming cannot mask sensitive data), and leave Automated Reasoning policies out of enforced guardrails. On bedrock-mantle, the OpenAI-compatible Chat Completions and Responses APIs, other providers and self-hosted models, apply the safeguards in your own gateway (for example with ApplyGuardrail), because enforcement and the IAM key cover only the four runtime APIs listed (as of 2026-10-07). For batch inference jobs, run ApplyGuardrail on outputs before release, or deny batch actions to roles that do not need them. Alert on invocation logs without the required guardrail.
- `sg_fail_closed`: Wrap every safeguard call with a timeout and an explicit failure branch that returns a safe response, and record that decision in logs and metrics. In pre-production, inject safeguard throttling, errors and timeouts, for example by stubbing the safeguard client, and confirm the safe response and the alarm. Enforced guardrails count toward the calling account's guardrail quotas in Service Quotas, so size guardrail quotas from peak text units with the model quotas and request increases where needed. Long inputs may need chunking to stay within the ApplyGuardrail text unit rate.

## `gai_runaway_cost`

- `sp_token_budgets`: Agree a budget per caller type and period with the business owner. Meter tokens per caller from the usage fields in each response, check the remaining budget at the entry point before every model call (in your own gateway for self-hosted and third-party models), and return a clear over-budget response. Test with one caller generating a surge while others keep working. Cost per request varies by orders of magnitude with tokens, and on Amazon Bedrock output tokens of some models count against quotas at a higher burndown rate, so size budgets in tokens, not requests.
- `sp_spend_stop`: Set the ceiling with the business owner. Alarm on token metrics in both namespaces (InputTokenCount and OutputTokenCount in AWS/Bedrock, TotalInputTokens and TotalOutputTokens in AWS/BedrockMantle), or on your own per-caller meter, and wire the alarm to automation that flips a feature flag, switches to a cheaper mode or applies a deny policy. Exercise the stop in pre-production and record how long it took. Outside AWS GovCloud (US), keep an AWS Budgets action as a backstop. For third-party APIs, combine provider spend limits with your own meter.
- `sp_spike_source`: Emit per-caller token metrics or add request metadata to invocation logs, build a top-callers query or dashboard, and rehearse finding the source of a synthetic spike within minutes. AgentCore harness: read token usage from the invocation-stream metadata events. Third-party APIs: meter the response usage fields.

## `gai_agent_bounds`

- `ab_no_actions`: If any tool or action has side effects, this scope exit does not apply: answer the other statements.
- `ab_single_enforcement`: Restrict each tool backend, and any runtime target, with a resource or IAM policy that admits only the gateway's role (AgentCore Runtime targets can be restricted so that only the gateway can invoke them). Use the gateway service role (IAM SigV4) for outbound auth where possible. With caller credentials, OAuth or token passthrough, restrict backends to credentials or audiences that only the gateway can obtain. Check the policyEngineConfiguration mode of every gateway. No separate condition key protects the mode beyond bedrock-agentcore:UpdateGateway, so limit UpdateGateway and policy engine changes to a named group, and alarm on those calls through CloudTrail. Review the tool list and backend policies at each release. With other frameworks, put tool calls behind one service that authorizes them and deny direct access to the backends.
- `ab_stop_exercised`: Write the stop runbook: who decides, the deny-all lever for all agents, and how in-flight sessions are ended. Keep a current record of active session IDs (for example from invocation logs) so StopRuntimeSession can be called for each one. Implement each lever on a path that does not depend on the agent runtime, rehearse it in pre-production or a game day, and record the time from the decision to the last tool call. On Amazon Bedrock AgentCore, StopRuntimeSession shares the runtime data plane quota, a gateway rate limit of 0 takes up to 30 seconds to apply, and rate limits fail open when the rate limit service is unavailable or a dimension cannot be resolved, so do not rely on a rate limit alone (as of 2026-10-09).
- `ab_limits_proven`: Strip or allowlist per-call overrides (model, limits, skills, additional parameters) at the entry point, add the runaway-loop test to pre-production, and alert on sessions that end at a limit.
