# Improvement plans: ORR - Mission-Critical Event Readiness 1.0.2

Generated by `python3 -m tools.orrlens docs` from `lens-src/`, the source of the release file `orr-event.json`. Do not edit by hand.

What to do when a statement is not in place, for the findings report. The questions and risk rules are in `lens-event.md`.

## `evt_calendar_freeze`

- `cf_dates`: Write a one-page event plan: the window, the key dates of every dependency and partner, measurable success criteria, and the readiness deadlines worked back from the event date. Review it with the business owner and every team and provider involved, and put the dates in the shared calendar that your deployment blockers and on-call schedules use. For a go-live or cutover, include success criteria for the cutover itself, for example data reconciled between the old and new systems, users able to complete each critical journey, and the conditions for falling back to the previous system.
- `cf_owner`: Name the event owner and a deputy, write go/no-go criteria and decision checkpoints, agree them with the accountable business owner, and record each checkpoint decision. Reuse the readiness decision from your core ORR review and add only the event-specific criteria.
- `cf_freeze`: Add the freeze period and the event window to the deployment blockers of every production pipeline, including configuration, feature-flag and operator-tool pipelines. Test in a non-production copy that a deployment is blocked, and document and rehearse the emergency override: who may approve it, how it is logged, and which checks still apply.
- `cf_final_review`: Schedule a short final review about two weeks before the event with the event owner, security and the on-call lead. Use a fixed checklist (open High risks and acceptance expiry dates, security findings, edge and rate-limit rules, privileged and emergency access), fix or accept each item before the freeze starts, and save a milestone so the pre-event state is recorded.

## `evt_peak_retest`

- `pr_forecast`: Hold a forecasting session with the business owner, marketing and partners. Collect data from comparable events, model the opening spike and the sustained peak, add automated traffic, retries and a worst case, and agree in writing the numbers and the margin that the load re-test must prove.
- `pr_retested`: Book the re-test 30-60 days before the event and after the last major change. Script the event's ramp, peak and duration at forecast plus margin, include real dependency paths only where each provider (for example a payment or identity provider) has agreed in writing to the test volume and window, otherwise use their sandbox or an approved stub, follow each provider's testing policy and the Amazon EC2 Testing Policy, fix what breaks and test again, and record the achieved rate, latency, errors and first bottleneck.
- `pr_alarms_validated`: Make alarm, scaling and runbook checks an explicit part of the re-test plan: list the alarms and actions you expect at each load step, have the event-window staff run them, record what happened, and fix and re-check any alarm or runbook that did not work.

## `evt_capacity_quotas`

- `cq_quotas_raised`: List the quotas each critical journey uses in every account and Region, including recovery Regions and third-party APIs. Compare them with the event forecast plus failover, request increases as soon as the forecast is agreed (large ones 3-6 months ahead, the rest at least 8 weeks ahead), confirm the applied values before the freeze, and add CloudWatch alarms on usage against the key quotas.
- `cq_capacity_secured`: From the forecast, work out the capacity needed at the opening minute and how fast you can add more. Reserve or pre-scale it for the event dates: request future-dated Capacity Reservations at least 8 weeks ahead where eligible and launch into them before the window, schedule minimum capacity to rise before the window, set provisioned concurrency or table throughput ahead of the peak, and confirm it is in place the day before.
- `cq_scale_down_plan`: Write the scale-down plan with the capacity plan: list every temporary resource and setting with its end date, the trigger for removing it (for example backlogs drained and traffic below a threshold for a day) and its owner, set an AWS Budgets alert for the event period, and schedule the scale-down as normal pipeline changes after the window. For a go-live or cutover whose capacity becomes the new baseline, record the decision to keep that capacity, its approved run-rate cost and a date to right-size it.

## `evt_ddos_response`

- `dd_not_public`: If any endpoint is internet-facing, answer the other statements instead. Keep the endpoint inventory current and guard it with a preventive control, so this scope exit stays true.
- `dd_l7_enforcing`: Inventory the web ACLs in front of event endpoints and record which DDoS mechanism each uses. Evaluate the Anti-DDoS rule group or rate-based rules in Count mode (its metrics and labels appear only during detected events, so also check the challengeable-request labels and exempt URIs), set Block (and Challenge where suitable) and the sensitivity before the freeze, confirm that the core paging alarms on DDoSAttackRequests and rate-based rule metrics cover these web ACLs, and pull the web ACL into IaC. Add rate-based rules wherever the rule group is not offered. If AWS Shield Advanced moved a web ACL to the Anti-DDoS rule group, review the settings it was given (as of 2026-10-14: Block or Count kept, sensitivity Low, Challenge off).
- `dd_ddos_tier`: Decide the DDoS tier with the event owner by weighing the event's visibility and the cost of downtime against the subscription, which as of 2026-10-14 includes access to the Anti-DDoS managed rule group and covers standard AWS WAF fees for protected resources up to a monthly request allowance; check AWS Shield Advanced and AWS WAF pricing for the managed rule group fees that still apply. If you subscribe, protect each resource, grant SRT access, set up proactive engagement with health checks and current contacts, and alarm on Anti-DDoS rule group events. If you do not, record the decision and the compensating controls.
- `dd_rehearsed`: Run a 60-minute DDoS tabletop with the event shift. Walk through detection, mitigation levers, AWS engagement and customer communications for a network flood and an HTTP request flood, time each step, fix gaps in the runbook, and confirm the cost protection prerequisites if you subscribe to Shield Advanced.

## `evt_rehearsal`

- `rh_tabletop`: Schedule a tabletop 4-8 weeks before the event. Write a scenario for each major risk with injects (for example, the payment provider times out 10 minutes into the peak), have the event shift respond from the real runbooks and dashboards, time the key decisions, and log every gap as a tracked finding.
- `rh_gameday`: Combine the game day with the load re-test or a second run. Agree stop conditions and a safe environment, inject the event's top faults at event-like load with AWS FIS or your own tooling, let the event shift respond without coaching, measure detection and mitigation times, and record the findings.
- `rh_findings_closed`: Track every rehearsal finding in the same tracker as your other operational work (for example AWS Systems Manager OpsCenter or your own tool), set due dates before the freeze, review open findings at each go/no-go checkpoint, and re-test the fixes for high-impact findings.

## `evt_war_room`

- `wr_staffing`: Build the event roster from the forecast and the risk list: name the incident lead, component operators, dependency contacts and communications lead for each shift, cap shift length, write a handoff checklist, and have everyone test their access to accounts, dashboards and runbooks a week before. Optional help such as AWS Countdown Premium (a paid add-on for Business Support+ and Enterprise Support, with one recurring subscription included in Unified Operations) can add AWS engineers to the plan; sign up 2-3 weeks before the event. Enterprise Support also includes AWS Countdown event management.
- `wr_escalation_tree`: Extend the core escalation paths into an event tree: list each component and dependency, primary and backup contacts and channels, and the AWS support path and severity to use. Two weeks before the event, test every contact, fix stale entries, and give the event shift an access-controlled offline copy (for example an encrypted file, or a printed copy held by the incident lead) that is destroyed or refreshed after the event.
- `wr_shared_channel`: Agree the channel and its fallback with each partner, and with AWS where your support plan or engagement provides for it, at least two weeks before the event. Test that every party can join, document who opens it and when, keep the joining details in the access-controlled offline copy of the escalation tree, and rotate bridge PINs or links after the event.

## `evt_degraded_modes`

- `dm_degraded_mode`: Choose the degraded mode that fits the critical journey, build it so the normal code path serves it rather than a rarely used fallback, add a configuration switch and an automatic trigger where safe, and test it at event-like load during the re-test or game day, timing how long it takes to engage.
- `dm_kill_switches`: List the features the event does not need, rank them by cost and value, wrap each in a feature flag read from dynamic configuration with a safe default, deploy flag changes through a validated configuration pipeline, and practice turning them off at load, recording how long each takes.
- `dm_status_comms`: Draft and pre-approve status messages for each likely situation with your communications and legal owners, list the stakeholders to notify and how, assign an approver to every shift, and rehearse publishing one message through the independent channel during the tabletop.

## `evt_post_event`

- `px_retro`: Book the review before the event so it happens within two weeks. Collect metrics against the forecast, the incident and near-miss log, and observations from the shift, partners and AWS; write the timeline and lessons without blame; and give each action an owner and a due date.
- `px_lessons_fed`: For each lesson, decide where it belongs: a core question answer, a new or revised question in your own add-on lens, the next event plan, or a runbook. Make the updates, then save post-event milestones on the core and event reviews and link them from the review document.
- `px_cost_review`: Run the scale-down plan as normal pipeline changes, confirm each temporary resource is removed or back at its baseline, compare the event-period cost with the budget in AWS Cost Explorer, and record the cost per unit of event demand to improve the next forecast. For a go-live or cutover whose capacity becomes the new baseline, record the decision to keep that capacity, its approved run-rate cost and a date to right-size it.
